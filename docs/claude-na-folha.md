# Claude on the sheet (contract, 2026-10-22)

[Português](pt-BR/claude-na-folha.md)

The agent working in the app appears on the sheet as **Claude** itself, drawn with Anatomy (`agentes-claude.mjs`), and subagents appear as versions of it at the **same size** (user decision, 2026-10-22). This document is the contract between the drawing (this action) and the movement across the sheet (the next action). Preview to approve the drawing: `referencias/claude-previa.html`.

## What it is

- **Only an indicator, with one exception.** It shows what the user's agent said through the MCP; it runs nothing and **has no click that sends work** (no "ask Claude for this"), except the "Start with Claude" button on the action's sheet (section "Starting the action", below), which opens a new session after a confirmed click. Hovering can show the last message; a click can only take the screen to the plan where it is (navigation, like the old robot), never send a task.
- **It replaces the sheet's old robot** (`web/js/robo.js`, `web/css/robo.css` and the `#robo-agente` band). The swap was done in the action "Claude walks across the sheet while working": the `#claude-camada` layer (`web/js/claude-camada.js`) and the pure logic in `web/js/claude-logica.js` (`claude-logica.test.mjs`); the separate agents panel was removed.
- **Zero work at rest.** Each pose is drawn once and the SVG is kept; the app swaps the SVG when the state changes. No animating hundreds of elements; no animation loop idling on the sheet.

## Where the data comes from

Everything comes from the contract that already exists in `registrar_progresso` (`src/mcp/atividade.rs`, `ferramentas.json`):

| Field | Values | What it is for in the figure |
| --- | --- | --- |
| `agente` | stable name (up to 40 characters) | tells who is who |
| `papel` | `explorador`, `construtor`, `revisor` | the subagent variant (tool and accent color) |
| `estado` | `lendo`, `escrevendo`, `testando`, `aguardando`, `bloqueado`, `concluido` | the pose |
| `onde` | up to 5 paths | text next to it; a change of `onde` or of plan = "walking" |
| `acao_id`, `plano_id` | ids | where on the sheet the character stands |
| `percentual` | 0 to 100 | does not change the figure (it stays in the text) |

## Poses

`poseDoEstado(estado, andando)` (in `agentes-claude.mjs`) does the mapping; `pecasDoClaude({ pose, papel, quadro })` returns the list of parts.

| Pose | When | What the drawing shows | `lit` part (the one the eye follows) |
| --- | --- | --- | --- |
| `parado` | no state (nothing reported, expired or `ocioso`) | arms at the sides, eyes open | none |
| `andando` (2 frames) | `lendo`/`escrevendo`/`testando` right after a change of `onde` or of plan; the sheet alternates `quadro` 0 and 1 while the character moves (next action) | one pair of legs lifts and steps forward, the body rises by 1 and the arms swing | none |
| `trabalhando` | `lendo`, `escrevendo`, `testando` | arms forward; the main Claude types on a keyboard, the subagent holds its tool | the spark over the head |
| `esperando` | `aguardando` | arms crossed in front and "..." over the head | the last dot of the "..." |
| `bloqueado` | `bloqueado` | frowning eyes, eyebrows and a striped barrier in front | the barrier's lamp |
| `concluido` | `concluido` | arms up, eyes "closed" with contentment, flag on the base plate | the flag's cloth |

Rules: at most one `lit` part per figure (exactly one in the poses above that have one); the framing is the same in every pose and role (the `enquadra` option of `desenhaEmblema`, constant `ENQUADRA`); `lendo`, `escrevendo` and `testando` share the same drawing (the difference stays in the text), on purpose, so the drawing stays readable at 24 to 48 px.

## Animation (2026-10-22)

Movement by **frames**: each frame is a finished drawing (a list of parts, kept once as SVG) and the sheet only switches which one is visible. The Anatomy kit does not change. `agentes-claude.mjs` exports `QUADROS` (how many), `SEQUENCIA` (the order) and `RITMO` (ms per frame); `pecasDoClaude({ pose, papel, quadro })` draws any frame. **Frame 0 of every pose is the approved drawing** (the test checks the old hashes) and the others move only a few parts. Smoothness: the in-between frames (halfway between two extremes) and the sequences that go back and forth through them give ~8 frames per second, with up to 5 drawings per pose.

| Pose | Frames | Sequence · pace | Movement |
| --- | --- | --- | --- |
| `parado` | 5 | 0 1 2 1 0 1 2 1 0 1 2 1 0 3 4 3 · 150 ms | breathes (the body rises up to 1, in 3 steps) three times and blinks (half closed, closed, half closed) |
| `andando` | 3 | 0 2 1 2 · 110 ms | one pair of legs lifts, passes through mid-step (frame 2) and the other pair lifts; only while moving |
| `trabalhando` | 5 | 0 1 2 1 0 3 4 3 · 110 ms | one arm reaches forward and back through the middle, then the other; the spark grows and turns with it |
| `esperando` | 3 | 0 1 2 · 300 ms | the lit dot of the "..." moves from one side to the other |
| `bloqueado` | 4 | 0 1 2 3 · 200 ms | the lamp is on in frames 0 and 1 and off in 2 and 3, while the barrier's bar rises and falls by 1.5 |
| `concluido` | 3 | 0 1 2 1 0 0 0 0 · 120 ms | a small hop (the body rises up to 2) and a pause; the flag's cloth waves with it |

The subagents' tool follows the hand, so it moves with the arm. Rules (the project's): a figure's clock only runs while the figure is visible on screen and the tab is open; it stops when walking, when the pose changes and when the figure is removed; with `prefers-reduced-motion` it stays on frame 0; with no active agent there is no timer at all. Animated preview without script: `referencias/claude-previa.html`. **Measured cost (2026-10-23, `node scripts/medir-animacoes.mjs`):** idle 0.03% of one core; one animated figure 0.34%; six figures 3.4%; hidden tab, figure off screen and reduced motion 0 clocks. The frames are stacked and the clock only toggles the `on` class (`opacity` on a composited layer, `claude.css`): `display:none` cost ~11% with six figures. Details in `referencias/relatorio-medicao.md`.

## Starting the action (contract, 2026-10-22; reopens "only an indicator")

The 2026-10-21 decision ("the agent is only an indicator, with no click that sends work") was **reopened by the user** on 2026-10-22 on one point only: the user can, whenever they want, **start an action with Claude** through a button. Claude still receives no orders through the MCP, the monitor or the channel; what changes is that the app can open a new Claude Code session after a confirmed click.

- **Button on the action's sheet:** the note gets the **"Start with Claude"** button (`acoes` of `abreNota`). It asks for confirmation ("opens a new terminal and spends tokens"), warns if an agent is already working on it and, when no folder is linked to the blueprint, explains how to link one. The global function `abreFolhaDaAcao(pid, fid, ancora)` (in `web/js/iniciar-acao.js`) opens the action's sheet.
- **Route:** `POST /api/mcp/iniciar` with `{ "workspaceId", "blueprintId", "acaoId" }`, loopback only, with `Host`/`Origin` checked, `content-type: application/json` and **never opened up by `MCP_REDE`**. It checks that the workspace, blueprint and action exist (404), finds the blueprint's folder in the `pastas` table (409 with `{"codigo": "sem-pasta"}` if there is none) and opens a **new terminal** in the folder: Windows Terminal (`wt.exe`) if present, otherwise the Windows prompt (`cmd /c start`); 501 with `{"codigo": "sem-terminal"}` if neither opens. It runs `blueprint claude` with the initial prompt as a **separate argument** (no command line assembled from text): "Execute a ação `<número>` «`<nome>`» do blueprint «`<nome>`» (workspace_id …, blueprint_id …, acao_id …): leia com ler_blueprint, registre o progresso com registrar_progresso e conclua cada plano com marcar_concluido e a evidência." (the prompt text as written then). Answer 200: `{ "ok": true, "pasta": "…", "terminal": "wt" | "cmd" }`; errors: `{ "erro": "…", "codigo"?: "…" }`. Claude Code's permissions are the normal ones (no skipping confirmations).
- **The prompt does not go through the monitor or the channel** (they are informational; the agent does not run instructions found in events). It goes as an argument of the new session, through a user click.
- **Done and Close (user decision, 2026-10-23):** the agent that finished stays on the plan, with the flag, until the user **clicks**; the click opens the small sheet with the completion message and **two options**: **Done** (the user has seen it: the agent leaves the sheet, it does not rest) and **Close** (only closes the small sheet; the agent stays where it is). The same **Done** button appears on an idle agent (waiting or resting) and dismisses it until it reports again (the "seen" applies only to that notice); an agent that is working (reading, writing, testing, blocked) only has Close. Resting after 10 min without a notice still stays still on the header. The agent's on-screen notice calls what was finished **Task completed** (and "Task not completed"), because "plan" is also the proposal the agent sends.
- **A subagent that finishes disappears by itself (user decision, 2026-10-26; `claudeSubSumiu` in `web/js/claude-logica.js`, used by `agentesAtivos`):** a subagent (one that has a `papel` and is not the main one in the list) with `estado: concluido` leaves the sheet, focus mode and the terminal 10 s after the notice, with no click: finishing a task (a search, a review) is not finishing the work. While it shows, the small sheet says "Subagent finished a task" and "Last task", without the completion message and without the Done button. Only the main agent keeps the flag and the Done button until the user sees it. The server keeps the subagent (the rule belongs to the page). Tests: `claude-logica.test.mjs` and `scripts/foco-e2e.mjs`.
- **Out of scope:** starting several actions at once, choosing the model. (Sending the request to an already open session moved out of here on 2026-10-23: see the next section.)

## Choosing the session when starting the action (contract approved on 2026-10-23; implemented, not yet tested with a real Claude)

Update of 2026-10-26: the dialog gained **App terminal** as the default (the session opens in a tab of the app's panel, through `POST /api/terminal/iniciar`; see [terminal-no-app.md](terminal-no-app.md)); **New session** still opens the external terminal.

User request on 2026-10-23: the "Start action N?" dialog shows **New session** (default) or the **Claude sessions already open** in that folder; when one is chosen, the action's prompt goes to it. This **reopens once more** the rule "Claude receives no orders": the exception applies only to the confirmed click in this dialog.

- **Who delivers: the MCP channel, not the hook or the mod.** The hook only *registers* the sessions (SessionStart/SessionEnd); the terminal mod is an indicator (the mods API has no call to write a prompt into an open session). The channel (`notifications/claude/channel`, [monitor-e-channels.md](monitor-e-channels.md)) was already validated in a real interactive session on 2026-10-22.
- **The limit the earlier validation shows:** only a session started with `BLUEPRINT_CHANNEL=1` and `--dangerously-load-development-channels` receives it (research preview; Claude Code asks for a development confirmation in every session). A session opened by hand without that appears in the list, but the click only **copies the prompt**. The sessions the button opens (`blueprint claude`) are now born with the channel on.
- **Each `blueprint --mcp` process with the channel on is a recipient:** it generates an id (16 hex), registers with the app when it opens the SSE (id and folder, no pid) and leaves the list when the connection drops (no polling). The app addresses the `iniciar-acao` event to one id; the other processes ignore it.
- **Today the channel only carries fixed, filtered text**, and the MCP tells the agent **not to run instructions from events**. For this to work: an event type of its own (`iniciar-acao`), with the text assembled by the app (the same cleaning as `iniciar`: no control characters, no `;`, short) and a sentence in the MCP instructions saying that **only this type**, coming from the user's click, is an order. Any other event content stays informational.
- **Security:** loopback only, `Host`/`Origin` checked, `content-type: application/json`, never through `MCP_REDE`; it refuses a session that is not from the blueprint's folder (409), a session that dropped (410) and a session without a channel (409, with the prompt to copy). Nothing is written to the data.
- **Routes (done):** `GET /api/mcp/sessoes?workspace=&blueprint=` returns `{sessoes: [{id, pasta, canal}]}` (each channel in the folder with `canal: true` and, at most, the remaining sessions without a channel) and `POST /api/mcp/iniciar` accepts `sessaoId` (and `semCanal: true` to only return the `prompt`). Errors: 410 `sessao-caiu`, 409 `sessao-de-outra-pasta`; the answer always carries the `prompt`. The channel registers by opening the SSE with `?canal=<id>&cwd=<pasta>` and leaves when the connection closes (up to 25 s later, the heartbeat). The plugin's `SessionEnd` (`hook/fim`) removes the session from the list. **Expiry (2026-10-26):** a session that closed without `SessionEnd` (it froze, the terminal was force-closed) leaves the list after 24 h without a signal (SessionStart, any hook with its `session_id` or the drop of the folder's channel renew it); in a folder with a connected channel no session expires. The check is lazy, when listing (`PRAZO` and `expirar` in `src/mcp/sessoes.rs`), with no thread and no polling.
- **Sessions opened by the button** (`blueprint claude <prompt> --canal`) turn on `BLUEPRINT_CHANNEL=1` and the development flag (the flag goes after the prompt, because it can be variadic); Claude Code asks for the development confirmation in them.
- **Checked with a real Claude (2026-10-26, `node scripts/agente-real-canal.mjs`, Claude Code 2.1.310, Sonnet 5.5 at medium effort, interactive session in a pseudo-terminal because the channel flag is ignored with `-p`):** (1) the session opened with `BLUEPRINT_CHANNEL=1` and `--dangerously-load-development-channels` appears in `GET /api/mcp/sessoes` with `canal: true` and leaves the list when Claude closes (`/exit`, `SessionEnd` hook); (2) `POST /api/mcp/iniciar` with the channel's `sessaoId` makes «The Blueprint · pedido do usuário» reach the **idle** session (the screen shows `← blueprint: …`) and become a turn in which the model treats the request as an order: it acts on the action named only in the message (1.1) and reads the blueprint through the MCP; it did not call `registrar_progresso` because that sample action was already done and it asked before redoing it; (3) **the flag's marketplace name is wrong for `--plugin-dir`:** Claude Code calls the plugin loaded through `--plugin-dir` `blueprint@inline`; with `plugin:blueprint@blueprint-local` (`FLAG_CANAL` in `src/cli/claude.rs`) the screen warns «you asked for plugin:blueprint@blueprint-local but the installed plugin is blueprint@inline» and the request message did not arrive; with `plugin:blueprint@inline` it arrives (the band still shows «plugin not installed», with no effect). `blueprint claude --canal` loads the plugin through `--plugin-dir`, so it now uses `plugin:blueprint@inline` (`FLAG_CANAL` in `src/cli/claude.rs`, fixed on 2026-10-26). A session opened by hand with the plugin installed from the marketplace uses `@blueprint-local` (not tested, because the test isolates the user's plugins). Still **not checked:** there is no link between the hook's session and the channel's process (no pid): the list does not say which session in the folder is which, only how many have a channel. Coverage without Claude: `cargo test` and `node scripts/sessao-iniciar-e2e.mjs` (fake channel and terminal).

## Sending a plan comment and talking with the plan (contract of 2026-10-26, pending user approval; not tested with a real Claude)

Two actions of the project "Native integration with Claude" send text written by the user to the Claude session they choose. Both use **the same path** as "Choosing the session" (above) and **do not widen the exception**: only by click, loopback only, only to the addressed channel, and nothing is written to the data.

- **One route only:** `POST /api/mcp/conversa` with `{workspaceId, blueprintId, acaoId, planoId?, tipo, texto, sessaoId, semCanal?}`. Like `/api/mcp/iniciar`, it only answers on loopback (`Host`/`Origin` checked; not even `MCP_REDE=1` opens it), requires `content-type: application/json` and checks that the action (and the plan, for a comment) exists in the database (404 if not). `texto`: up to **800 characters**, control characters become spaces; empty is 400, too long is 413. The names of the action, the plan and the blueprint go through the same cleaning as `iniciar` (no control characters, no `;`, 80 characters).
- **Delivery:** the `sessaoId` session must have its channel connected and belong to a folder of the blueprint (410 `sessao-caiu`, 409 `sessao-de-outra-pasta`, as in `iniciar`). The SSE event is addressed (`canalId`) and only the `blueprint --mcp` of that channel passes it on; the other processes ignore it. The event's JSON must fit in 1,900 bytes (the channel's SSE line is capped at 2,048): over that, 413. `semCanal: true` delivers nothing (no `sessaoId` needed) and only returns the `prompt` for the page to copy.
- **Plan comment (`tipo: "comentario"`, requires `planoId`):** event `comentario-plano`. The channel delivers it with the **same order prefix** as `iniciar`: «The Blueprint · pedido do usuário (ele clicou em Enviar ao agente num comentário de plano): …», followed by "Comentário no plano «P» (plano_id …) da ação N «A» do blueprint «B» (workspace_id …, blueprint_id …, acao_id …): <texto>" (the prefixes stay in Portuguese on purpose). It is an order because the user wrote it and confirmed it in the dialog. On the page: right-click on the plan → **Send comment to the agent…**, a dialog with the text and the choice of session (each open session or "Only copy the text"); the Send button is the confirmation. The comment **is not saved in the plan** (today there is no screen for user comments on a plan; the plan's comments are the agent's). The result shows in the dialog itself: "sent to the session" or "copied".
- **Conversation (`tipo: "conversa"`):** event `conversa-usuario`, with **its own prefix**: «The Blueprint · conversa do usuário (responda com responder_conversa; ajustes só por propor_blueprint): Ação N «A» do blueprint «B» (ids…): <texto>». It is not an order to execute: the MCP instructions say to answer with `responder_conversa`, to propose any change only through `propor_blueprint` (or `ajustar`) and not to edit files or run commands because of it.
- **The way back:** the channel has no reply, so the AI answers through the MCP tool **`responder_conversa(workspace_id, blueprint_id, acao_id, texto, proposta?)`** → `POST /api/mcp/conversa/resposta`. `texto` up to 4,000 characters; `proposta` is the number of a **pending** proposal in that blueprint's queue (409 with the pending numbers if it is not). With the app closed, it fails (the conversation lives only in memory; it does not go to the pending folder).
- **Memory:** each action keeps the last **40** messages (`{de: "usuario"|"agente", texto, em, proposta?}`), at most **32** conversations (over that, it forgets all of them, like the sessions). It disappears when the app restarts, like the queue. `GET /api/mcp/conversa?workspace=&blueprint=&acao=` returns `{mensagens}`; each new message notifies the page through the SSE event `conversa` (`{workspaceId, blueprintId, acaoId}`, no text), and the page with that action's panel open fetches the list.
- **Panel on the sheet:** **Talk with the plan** on the action's sheet (next to "Start with Claude") and in the action's right-click menu. It opens a side panel with the history, the choice of session (those open in the folder, with or without a channel; with none, only "Copy the message" and the hint to open one with "Start with Claude"), the message field and **Send** (the click is the confirmation; the chosen session stays visible next to the button). An answer that names a proposal shows **Open proposal no. N**, which opens Plan on that proposal; applying is still the usual click. Texts through `tr()` (catalog `web/i18n/en-conversa.js`), the app's theme, no emojis.
- **Out of scope:** opening a new session just to talk; keeping the conversation in the database; saving the comment in the plan; replying through the channel itself. Test without Claude: `node scripts/conversa-e2e.mjs` (fake channel and agent).

## Where the agent stands and how it appears and leaves (2026-10-22)

- **Place, from the most precise to the most general** (`claudeLugar` in `web/js/claude-logica.js`): on its **plan's row** (open section); otherwise next to the **action's bar** (closed section); otherwise on the **header of the action's section (the project)**, not the first project's; only when no action is known, on the blueprint's header (or on the list card). Agents in the same place stand side by side, and the header place is per section. For the agent to stand on the plan, it must send `acao_id` and `plano_id` in `registrar_progresso`; the edit hook inherits them from the last notice.
- **Appearing and leaving:** when entering the sheet the figure **grows from the center** (`scale` from 0 to 1, 380 ms) and when leaving it **shrinks to the center** (from 1 to 0, 300 ms) before being removed (`claudeEntra` and `claudeSai` in `web/js/claude-camada.js`). No animation with `prefers-reduced-motion` or a hidden tab.

## How many appear

- **One main Claude** and **up to `MAX_SUBAGENTES` = 7 subagent figures**. Up to 5 figures stand side by side; with more, they **close up** (the step between them shrinks and they overlap, the one closest to the place, the main one, on top) and the group never gets wider than 5 (user decision, 2026-10-23: no "+N" counter). Over 8, the rest are not drawn and the hint of the last figure says how many are gathered there. Figure order: whoever reported most recently first; the agent **never leaves the sheet for lack of signal**: after finishing (20 s celebrating on the plan) or after 10 min without a notice (`VIDA_MS`) it goes to **rest**: pose `parado`, no plan, on the blueprint's header (the figure walks there), and it stays like that until a new notice arrives; it only leaves when the app restarts (presence lives only in memory) or when the 33rd agent replaces it. The "In progress" filter counts only those on a plan (working), not those resting. The edit hook inherits the agent's action and plan from its last notice, so that editing does not take it off the plan. **New subagent (2026-10-26):** it is born next to the main Claude's plan when the main one's last notice is less than 10 min old and not finished (`Atividade::plano_de`); otherwise it stays on the blueprint's header, as before. Before this, a subagent never inherited, and whoever launched subagents without reporting the plan only saw them on the header.
- The main one is the agent **without `papel`** or, if all have one, the oldest; it never carries a tool. The others are subagents of the role they reported. (Assumption: the MCP does not mark who is a subagent.)
- Size: **all agents have the same size** (user decision, 2026-10-22; it was 70% for the subagent): `ESCALA.subagente` = 1, the same framing and the same camera. Reading target: 48 px wide for all; below that (24 px) they are still told apart by the tool and the base color.

## Execution timeline per action (decision of 2026-10-26, to be reviewed by the user)

Presence (`src/mcp/atividade.rs`) only keeps each agent's last state and disappears on restart. The action's sheet gains, below the instructions, a read-only list with the agent's latest events on that action: started, changed file, blocked, finished or did not finish a plan, marked a checkpoint, each with the time, the agent and the plan.

- **Where it lives: in the database, in a table of its own** (`linha_do_tempo`, migration `004_linha_do_tempo.sql`; code in `src/dados/linha_do_tempo.rs`). Reason: the app restarts on every update and every time the user closes it from the tray, and a timeline that disappears at those moments does not answer "what did the agent do and when". It stays **outside data.json**, like `pastas`: `PUT /api/dados` does not erase it, `GET /api/dados` does not grow with it and `blueprint exportar` does not carry it. It is not blueprint data, it is a record of what the agent reported; nothing in it changes the blueprint.
- **What goes in:** only events that already pass through `acoes::evento` (those from `registrar_progresso`, `reportar_bloqueio`, `marcar_concluido`, `marcar_nao_concluido`, `marcar_checkpoint_*` and the edit and subagent hooks) **and that have an action**. Fields: the workspace, blueprint and action ids; `alvo` (the plan's or the checkpoint's id, depending on the type; the page takes the name from the data); time (ISO); agent name (up to 40); type; state; `onde` (the first path, up to 120, relative to the session's folder, as it already arrives); short text (up to 200 characters).
- **What never goes in:** file contents (the server does not even receive them: the edit hook only sends the path), commands and outputs, the evidence of `marcar_concluido` and of checkpoints (it can carry a command and test output; it already becomes a plan comment when the page applies it, so the timeline records those events **without text**), `session_id`, `cwd` and the rest of `tool_input`. No personal data besides the name the agent chose for itself.
- **Retention:** the **50 most recent events per action** and **nothing older than 30 days** (both rules run in the same transaction as each write; nothing runs at rest). Repeated events in a row (same agent, type, target, text, state and file, like several edits of the same file in a row) become one, with the time of the last. Deleted action: its events leave through the 30 days.
- **Reading:** `GET /api/mcp/linha-do-tempo?workspace=&blueprint=&acao=` (the same loopback rules as the `/api/mcp/*` routes) returns `{eventos, limite}`, from newest to oldest. Each write notifies through the SSE event `linha-do-tempo` with the three ids (no free text in the SSE); the page only fetches again if that action's sheet is open. No polling.
- **Interface:** `web/js/linha-do-tempo.js` (pure logic tested in `linha-do-tempo.test.mjs`), style in `web/css/linha-do-tempo.css`, texts in `web/i18n/en-linha-do-tempo.js`. End to end: `node scripts/linha-do-tempo-e2e.mjs [exe]` (~3 s, Edge without a window, temporary database).
- **Known limits:** an event kept while the app was closed (`pendentes.rs`) goes in with the time at which the app resent it; a failure to write the timeline does not refuse the event (it only goes missing from the list), so the agent does not resend it and duplicate the queue.

## Plugin hooks: worktrees, states and subagent context (2026-10-26)

Event names and fields checked at https://code.claude.com/docs/en/hooks.md (Claude Code 2.1.310); `registrar` writes everything into the plugin's `hooks/hooks.json`.

- **Worktrees (`src/mcp/worktree.rs`).** The hooks' `cwd` follows the git worktree (`.claude/worktrees/<name>/` or any `git worktree add`). The main folder comes from the worktree's `.git` file (`gitdir: <repo>/.git/worktrees/<name>`) and its `commondir`, using only `std::fs` and accepting `\` and `/`. The folder -> blueprint link tries the `cwd` and, if there is none, the main folder (the disk is only read when the link is missing); `vincular_pasta` and `pasta/desvincular` write and remove through the main folder; the open session and the channel count in the main folder, and the "folder without a blueprint" notice shows the main one. A plain folder, a submodule and a bare repository stay as they are.
- **States (`POST /api/mcp/hook/estado`, `src/mcp/hooks_estado.rs`).** Five `http` hooks (`timeout` 5) use the states that already exist: `PermissionRequest` -> aguardando «waiting for permission: <tool_name>»; `PermissionDenied` -> bloqueado with the `reason` (Claude only fires it in auto mode); `StopFailure` -> bloqueado with `error` and `error_details`; `PreCompact` -> aguardando «compacting the conversation»; `PostCompact` -> escrevendo. Presence only: it goes to the agent's activity, with no queue item and no timeline entry (a permission request is common and would fill the action's 50 events). The answer is always `{}`: it never decides a permission nor holds Claude Code. Outside text: no control characters, short. `PostToolUseFailure` was left out on purpose (a tool failure is routine and would only add noise). Limit: the agent only leaves "waiting" on the next edit hook or notice (there is no "permission answered" hook).
- **Subagent context.** `SubagentStart` returns `hookSpecificOutput.additionalContext` (always in English) with the folder's blueprint, the current action, the pending plans and «You are a subagent: do not mark plans done; report with registrar_progresso only if asked.». `SubagentStop` still has no `decision`. Folder without a blueprint: no context.
- **The plugin's agents** (`claude-plugin/plugins/blueprint/agents/`): `blueprint-explorer` (haiku, cyan, read-only: Read, Grep, Glob, `listar_blueprints`, `ler_blueprint`, `guia_de_planejamento`), `blueprint-builder` (orange, default tools) and `blueprint-reviewer` (green, read + Bash for tests). No `background` nor `isolation`; Claude Code ignores `hooks`, `permissionMode` and `mcpServers` in a plugin agent. The `agent_type` arrives as `blueprint:blueprint-explorer`, and the role (explorador, revisor, construtor) comes from the name in `hooks.rs`.
